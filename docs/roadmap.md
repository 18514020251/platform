# 项目优化路线图

> 本文档用于记录项目后续优化方向和开发优先级，避免为了堆技术栈而盲目增加复杂度。  
> 当前项目定位：**轻量化企业智能知识库与流程协同平台**，重点体现后端工程能力、业务建模能力和系统设计取舍。

---

## 1. 当前项目定位

本项目不是为了堆砌中间件，而是围绕以下目标进行设计：

- 支持用户认证、角色权限、网关转发等基础后端能力；
- 支持工单创建、接单、分派、处理、状态流转等业务流程；
- 支持知识库文档处理、全文检索、向量检索和 RAG 问答；
- 支持访问日志采集、traceId 链路标识和敏感字段脱敏；
- 保持本地部署简单，避免为了展示技术栈而引入过重架构。

---

## 2. 优先级说明

后续优化按照优先级分为四类：

| 优先级 | 含义 |
|---|---|
| P0 | 面试前必须补，直接影响项目专业度 |
| P1 | 强烈建议补，能明显提升后端含金量 |
| P2 | 有时间再补，属于增强项 |
| P3 | 暂不建议做，容易增加复杂度或偏离项目定位 |

### 4.4 知识库任务状态表

当前不建议直接上 MQ，可以先用任务状态表实现轻量异步处理。

建议状态：

| 状态 | 说明 |
|---|---|
| PENDING | 待处理 |
| PROCESSING | 处理中 |
| SUCCESS | 处理成功 |
| FAILED | 处理失败 |

建议字段：

| 字段 | 说明 |
|---|---|
| id | 主键 |
| doc_id | 文档 ID |
| status | 任务状态 |
| retry_count | 重试次数 |
| error_message | 错误原因 |
| started_at | 开始时间 |
| finished_at | 结束时间 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

建议流程：

```text
用户上传文档
  ↓
保存文档记录
  ↓
创建处理任务，状态为 PENDING
  ↓
定时任务扫描 PENDING / FAILED
  ↓
解析文档、文本切片、生成 embedding、写入 ES
  ↓
更新任务状态
```

面试表达：

> 当前项目定位轻量化部署，因此没有强行引入 MQ。对于文档解析和向量化这类耗时任务，先采用任务状态表 + 定时补偿机制，保证任务可追踪、可重试、可恢复。后续在任务量提升后，可以平滑替换为 MQ 消费模型。

## 6. P3：暂不建议做

### 6.1 暂不全面引入 MQ

当前不建议为了简历展示强行上 MQ。

原因：

- 增加部署复杂度
- 增加消息可靠性设计成本
- 增加重复消费、失败重试、死信队列等问题
- 如果业务量不大，收益不明显
- 面试时容易被追问实现细节

可以保留后续演进说明：

> 当前版本采用任务状态表 + 定时补偿机制。后续如果知识库文档处理量增大，可将任务分发替换为 RabbitMQ，实现削峰、解耦和异步消费。

---

### 6.2 暂不做复杂分布式事务

当前项目没有必要引入 Seata 或复杂分布式事务方案。

建议优先使用：

- 本地事务
- 状态表
- 幂等设计
- 补偿任务
- 最终一致性说明

---

### 6.3 暂不做 Kubernetes 部署

当前 Docker Compose 已经足够用于本地演示和简历展示。Kubernetes 可以作为未来扩展，不建议现在投入过多时间。

## 8. 面试讲解重点

面试时建议重点讲这几个点：

### 8.1 为什么没有一开始引入 MQ？

可以回答：

> 项目当前定位是轻量化部署和快速演示，核心业务量不大。如果一开始就引入 MQ，会增加部署复杂度和可靠性设计成本。因此我先采用任务状态表 + 定时补偿机制处理文档解析和向量化任务。这样既能实现异步和失败重试，也能保持系统简单。后续如果任务量提升，可以平滑演进到 MQ 消费模型。

---

### 8.2 怎么保证工单不会被多人同时接单？

可以回答：

> 接单时不是先查再改，而是使用带状态条件的 update，例如只允许 `status = NEW` 的工单被更新。并发情况下只有一个请求能更新成功，其他请求 update 结果为 0，从而避免多人接单成功。

---

### 8.3 RAG 链路怎么设计？

可以回答：

> 文档进入知识库后，会经过解析、切片、embedding 生成和索引写入。查询时同时进行全文检索和向量检索，再通过混合排序合并结果，最后将召回片段作为上下文传给大模型生成回答。后续会补充引用来源、最低分阈值和 prompt injection 防护。

---

### 8.4 日志系统有什么价值？

可以回答：

> 我封装了访问日志 starter，通过 AOP 采集请求信息，结合 MDC 生成 traceId，支持敏感字段脱敏，并将日志写入 MongoDB。这样业务服务可以低侵入接入统一日志能力，便于后续排查接口问题和追踪请求链路。

## 9. 简历优化方向

当前可写：

```text
企业智能知识库与流程协同平台
技术栈：Spring Boot、Spring Cloud Alibaba、Sa-Token、MyBatis-Plus、Redis、Elasticsearch、MongoDB、LangChain4j、Docker Compose

- 设计并实现企业智能知识库与流程协同平台，采用多模块微服务架构，拆分网关、认证、工单、知识库、AI 助手、日志等服务。
```

## 10. 当前结论

当前阶段最应该做的是：

```text
1. 不急着上 MQ
2. 先补工单操作历史
3. 再补知识库任务状态表
4. 然后补关键测试
5. 最后再做限流、CI 和部署优化
```

项目优化的核心原则：

> 不为了显得高级而堆技术栈，而是围绕业务问题选择合适复杂度的方案。
